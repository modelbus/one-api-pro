# v0.0.22 — 用户管理批量操作（删除 / 禁用）

> 管理后台「用户管理」页面新增批量选择 + 批量删除 / 批量禁用能力：复选框全选 / 半选、跨页选中持久化、arco 二次确认弹窗、红色危险样式。`POST /api/user/manage` 同时新增批量分支（root-only），单次请求支持对一组用户名执行删除或禁用，部分失败返回明细并写入 `LogTypeManage` 日志；单条删除 / 禁用同步收紧为 root-only，与 promote / demote 保持一致。
>
> The admin user-management page gains batch selection and bulk delete / disable: select-all / indeterminate checkboxes, cross-page selection persistence, an arco confirm modal and red danger styling. `POST /api/user/manage` now also exposes a batch branch (root-only) so a single request can delete or disable a set of usernames; partial failures return a per-row breakdown and are written to `LogTypeManage`. Single delete / disable are tightened to root-only to stay consistent with promote / demote.

## 中文

### ✨ 新增功能

- **用户管理批量操作（删除 / 禁用）**（`web/default-pro/src/views/user/User.vue` + `controller/user.go`）：
  - 列表左侧第一列新增 `a-checkbox`，表头复选框支持全选 / 半选（`indeterminate` + `model-value`），符合 arco 设计规范。
  - 「root」用户（`role >= 100`）行的复选框自动 `disabled`，并配合 `a-tooltip` 给出说明，避免误选导致整批失败。
  - 分页行左侧新增批量操作 `a-dropdown`，内含「批量删除」「批量禁用」两个 `a-doption`（沿用 `AdminLayout` 的 `#icon` 槽写法）。
  - `selectedUsernames` 跨页持久化，操作成功后只保留仍然存在的项、清理已被删除的项；进入搜索模式时自动清空，避免跨上下文误操作。
  - 列表底部 `.list-footer` 改为 flex `space-between`，左侧是批量操作区、右侧是分页器。
- **批量操作二次确认 + 红色危险样式**（`User.vue`）：
  - 批量删除 / 禁用改用 arco `<a-modal>` 二次确认（参考 arco.design/vue/component/modal 文档），单一 Modal 复用，title / content / ok-text 由 `batchConfirmAction` 计算切换。
  - 批量删除的 OK 按钮加 `ok-button-props={ status:'danger' }`，高亮为红色危险操作。
  - 下拉触发按钮的 icon 从 `#icon` 槽（左侧）改为内联 `icon-down`（右侧），对齐 arco 推荐用法。
  - 「批量删除」下拉项加 `class='batch-opt-danger'`，文字 + 图标变红、悬停浅红背景，列表单条删除按钮 `.danger-btn` 默认红色、禁用时回到灰色。
  - 新增 `IconExclamationCircle` 与 `.batch-confirm-body`（左侧红色感叹号 + 内容），让确认弹窗的视觉风险提示与 arco 通用约定一致。
- **批量操作完整 i18n**（`web/default-pro/src/i18n/pages/userPage.js`）：
  - 新增 `batchOperate` / `batchDelete` / `batchDisable`、`selectedCount`（`{n} 项` / `{n} selected`）、`confirmBatchDelete` / `confirmBatchDisable`（`{n}` 占位）。

### 🔒 安全

- **单条 / 批量删除与禁用收紧为 root-only**（`controller/user.go::ManageUser` / `manageUserBatch`）：
  - 历史上非 root 管理员也能删除 / 禁用其他用户，本次与 `promote` / `demote` 对齐，单条与批量两条路径均改为 root-only，避免越权清理用户。
  - 该行为变更仅影响「删除 / 禁用」两类高危动作；其它管理动作（升降权、重置密码、备注等）权限未变。
  - 前端操作入口已同步收紧：非 root 管理员在用户管理页看不到「删除」按钮，点击批量菜单也会被后端拒绝并通过 `userPageBatchFailed` 提示。

### 🐛 问题修复

- **批量失败无明细**：老接口每次只能处理一个用户，root / 自己 / 不存在的用户名会直接中断整批操作。新接口统一走 `failed` 明细返回，全部失败返回 `success:false`，部分失败返回 `success:true` 并附 `data.failed`（用户名 → 原因）+ `succeeded_count` / `failed_count`，UI 可精准提示「哪些行被跳过」。
- **批量操作无审计**：删除 / 禁用成功现在都会写一条 `LogTypeManage` 日志（含「管理员批量删除 / 禁用用户」），可在「日志查询」页直接追溯。
- **批量删除 / 禁用空选择被误判成功**：空 `usernames[]` 直接返回 `success:false` + 错误信息，杜绝前端误传空数组导致接口被当成无操作放过。

### 🔧 重构

- **用户管理页移除「编辑个人资料」入口**（`User.vue`）：
  - 删除搜索栏右侧「编辑个人资料」按钮以及对应的 `selfEditVisible` / `selfEditForm` 状态、modal、`openSelfEditModal` / `handleSelfEdit` / `resetSelfEditForm` 函数与未使用的 `IconEdit` import。
  - 「编辑个人资料」功能已迁移到 `AdminLayout` 右上角用户名下拉菜单，这里属于冗余入口，留着只会让用户分不清去哪改资料。

### 🧪 测试

- **`POST /api/user/manage` 批量分支单测**（`controller/user_test.go`）：
  - `batch_disable_non_root_forbidden`：非 root 管理员调用批量禁用必须被拒绝，且两个目标用户仍处于启用态。
  - `batch_delete_root_success_partial`：root 批量删除 2 个普通用户 + 1 个 root 用户，断言 `success=true`、`succeeded_count=2`、`failed_count=1`、`failed.root1` 有值；两个普通用户落库为 `UserStatusDeleted`。
  - `batch_all_failed_returns_success_false`：root 调用 `["root1"]` 把自己算进去时必须返回 `success=false`，未在批次中的无关用户保持启用态。
  - `batch_empty_usernames_rejected`：空 `usernames` 必须返回 `success=false`。
  - 顺带把 `model.Log` 加入 `TestMain` 的 `AutoMigrate`，并把 `model.LOG_DB = db` 接好，让批量操作的日志断言可以在 in-memory SQLite 里直接跑。

### ⚠️ 升级注意事项

- **零数据库迁移**：本次不涉及任何表结构变更。
- **行为变更 — 删除 / 禁用收紧为 root-only**：自 v0.0.22 起，**非 root 管理员不再能删除或禁用其他用户**（含已有功能按钮隐藏，但通过 API 直接调用也会被拒绝）。如果你的运维约定依赖非 root 管理员清理用户，请把对应账号升级为 root，或在管理后台把目标用户交给 root 处理。
- **需要重新构建前端**：`web/default-pro/` 的修改需 `npm run build` 后重新 `//go:embed` 进二进制。
- **API 兼容性**：`POST /api/user/manage` 单条路径的请求体不变，新增 `usernames[]` 字段即进入批量分支；老调用方不受影响。
- **批量操作审计**：批量删除 / 禁用成功后会在「日志查询」生成 `LogTypeManage` 日志，运维可按日志检索管理员批量动作。
- **构建与测试**：
  - `go build ./...` 通过。
  - `go test ./model/ ./controller/ ./middleware/` 全绿（含新增的批量分支 4 个子测试）。
  - `cd web/default-pro && npm run build` 通过。

## English

### ✨ New Features

- **Bulk user operations (delete / disable)** (`web/default-pro/src/views/user/User.vue` + `controller/user.go`):
  - Adds an `a-checkbox` as the first column of the list; the header checkbox supports select-all / indeterminate (`indeterminate` + `model-value`), per arco design conventions.
  - Root users (`role >= 100`) are auto-disabled with an `a-tooltip` explaining why, so a batch is never silently rejected because one row was unselectable.
  - A `a-dropdown` is added to the left of the pagination row with two `a-doption`s — "Batch Delete" and "Batch Disable" — using the same `#icon` slot pattern already used in `AdminLayout`.
  - `selectedUsernames` persists across pages; after a successful operation the list keeps only entries that still exist and prunes the rest. Entering search mode clears the selection to avoid cross-context accidents.
  - `.list-footer` is converted to a flex `space-between` row with the batch toolbar on the left and the pagination on the right.
- **Second-step confirm + danger styling** (`User.vue`):
  - Batch delete / disable now go through an arco `<a-modal>` confirm step (per arco.design/vue/component/modal docs); a single reusable modal is shared, with `title` / `content` / `ok-text` driven by a computed `batchConfirmAction`.
  - The batch-delete OK button uses `ok-button-props={ status:'danger' }` to render red.
  - The dropdown trigger's icon moves from the `#icon` slot (left) to an inline `icon-down` (right), matching arco's recommended layout.
  - The "Batch Delete" `a-doption` gains `class='batch-opt-danger'` — red text + icon + light-red hover. The per-row delete button (`.danger-btn`) is red by default and falls back to gray when disabled.
  - A new `IconExclamationCircle` plus `.batch-confirm-body` (red exclamation + content) gives the confirm modal a clear visual risk cue aligned with arco's general conventions.
- **Full i18n for the new flow** (`web/default-pro/src/i18n/pages/userPage.js`):
  - New keys: `batchOperate` / `batchDelete` / `batchDisable`, `selectedCount` (`{n} selected`), `confirmBatchDelete` / `confirmBatchDisable` (with `{n}` placeholders).
  - New keys for partial results: `batchAllFailed` / `batchPartialResult` (`{ok} {fail}`), `batchRootSkipped` / `batchCannotIncludeSelf` / `batchEmptySelection` / `userPageBatchFailed`.
  - New modal titles: `batchConfirmDeleteTitle` / `batchConfirmDisableTitle`.
  - Dead strings (`editProfile` / `userNotLoaded` / `selfEditSuccess` / `updateFailed`) are removed to keep the message bundle from drifting.

### 🔒 Security

- **Single + batch delete/disable tightened to root-only** (`controller/user.go::ManageUser` / `manageUserBatch`):
  - Previously any non-root admin could delete or disable other users. The new code aligns single + batch paths with `promote` / `demote`: root-only, no exceptions.
  - Only the two high-risk actions (delete / disable) are affected; every other admin action (role change, password reset, remark, etc.) keeps its existing permissions.
  - The UI hides the buttons for non-root admins, and any direct API call from a non-root admin is rejected with a `userPageBatchFailed` toast.

### 🐛 Bug Fixes

- **Batch failures had no per-row detail**: the legacy handler operated on a single user, so root / self / unknown usernames aborted the entire batch. The new handler returns a `failed` map (`username → reason`), `succeeded_count`, and `failed_count`; the UI can now tell operators exactly which rows were skipped.
- **Bulk operations left no audit trail**: every successful single or batch delete/disable now writes a `LogTypeManage` entry (including "admin batch-deleted / batch-disabled user"), directly visible in the **Logs** page.
- **Empty selection silently passed as success**: an empty `usernames[]` is returned as `success:false` with a clear error, so a buggy client can no longer make a no-op call look like a successful batch.

### 🔧 Refactor

- **Removed the redundant "Edit Profile" entry from the user-management page** (`User.vue`):
  - Removes the right-side Edit-Profile button on the search bar along with the `selfEditVisible` / `selfEditForm` state, the modal, the `openSelfEditModal` / `handleSelfEdit` / `resetSelfEditForm` helpers, and the now-unused `IconEdit` import.
  - "Edit Profile" has already moved to the top-right user dropdown in `AdminLayout`, so the per-page entry was dead weight and only confused users.

### 🧪 Tests

- **`POST /api/user/manage` batch branch unit tests** (`controller/user_test.go`):
  - `batch_disable_non_root_forbidden`: a non-root admin's batch-disable call must be rejected, and both target users must remain enabled.
  - `batch_delete_root_success_partial`: a root deletes 2 ordinary users + 1 root user; asserts `success=true`, `succeeded_count=2`, `failed_count=1`, `failed.root1` is present, and the two ordinary users land in `UserStatusDeleted` in the DB.
  - `batch_all_failed_returns_success_false`: a root calling `["root1"]` (including themselves) must return `success=false`; unrelated users stay enabled.
  - `batch_empty_usernames_rejected`: empty `usernames` must return `success=false`.
  - `model.Log` is added to `TestMain`'s `AutoMigrate` and `model.LOG_DB = db` is wired up so the log assertions can run against in-memory SQLite directly.

### ⚠️ Upgrade Notes

- **Zero database migration**: no schema changes.
- **Behavior change — delete / disable are now root-only**: starting with v0.0.22, **non-root admins can no longer delete or disable other users** (the button is hidden in the UI, and direct API calls are rejected). If your ops process relies on non-root admins to clean up users, either promote the relevant account to root or hand the user off to a root admin.
- **Frontend rebuild required**: changes under `web/default-pro/` need `npm run build` so the new assets are re-embedded into the Go binary.
- **API compatibility**: `POST /api/user/manage` keeps its single-user request body unchanged; supplying a `usernames[]` field routes to the new batch branch, so existing callers are unaffected.
- **Audit trail**: every successful batch delete / disable produces a `LogTypeManage` entry, so admin bulk actions are searchable from the **Logs** page.
- **Build & test**:
  - `go build ./...` passes.
  - `go test ./model/ ./controller/ ./middleware/` is green (4 new batch-branch subtests).
  - `cd web/default-pro && npm run build` passes.
