## 🚀 البدء السريع

### 1. الحصول على الملف التنفيذي

قم بتنزيل النسخة المترجمة مسبقًا من صفحة [GitHub Releases](https://github.com/modelbus/one-api-pro/releases/latest)، أو قم بالبناء من المصدر:

```bash
git clone https://github.com/modelbus/one-api-pro.git
cd one-api-pro
```

### 2. (البناء من المصدر) بناء واجهة Vue 3 الأمامية

```bash
cd web
sh build.sh        # يبني تنسيقات web/THEMES بالتتابع (الافتراضي default-pro)
cd ..
```

### 3. (البناء من المصدر) بناء الواجهة الخلفية

> يجب بناء الواجهة الخلفية بعد اكتمال بناء الواجهة الأمامية، لتضمين أحدث ناتج للواجهة الأمامية.

```bash
go build -ldflags "-s -w" -o one-api-pro
```

### 4. (اختياري) التغليف متعدد المنصات بضغطة واحدة

استخدم سكربت `release.sh` في الجذر لتنفيذ تنزيل الاعتمادات وبناء الواجهة الأمامية والترجمة المتقاطعة متعددة المنصات خطوة واحدة:

```bash
./release.sh                          # يستخدم ملف VERSION كرقم الإصدار
./release.sh v0.1.0                   # تحديد رقم إصدار
./release.sh v0.1.0 --skip-frontend   # تخطي بناء الواجهة الأمامية (إعادة استخدام web/build)
```

> الاعتمادات المسبقة: `go` و `node` و `npm`. رقم الإصدار مأخوذ من ملف `VERSION` في الجذر (يتوافق تلقائيًا مع وجود أو غياب سابقة `v`).

نواتج التغليف عبارة عن **ملفات تنفيذية مجردة مترابطة بشكل ثابت** (لا حاجة لفك الضغط، تُشغّل مباشرة)، وتُكتب إلى دليل `dist/`:

```
dist/one-api-pro-linux-amd64
dist/one-api-pro-linux-arm64
dist/one-api-pro-windows-amd64.exe
dist/one-api-pro-darwin-amd64
dist/one-api-pro-darwin-arm64
```

> نسخ `linux-*` مترابطة بشكل ثابت وتعمل على CentOS / Ubuntu. نبني GitHub Releases تلقائيًا عبر `.github/workflows/release.yml` عند دفع وسْم `v*`، بما يتوافق مع ناتج `release.sh` المحلي.

### 5. التشغيل

```bash
./one-api-pro --port 3000 --log-dir ./logs
```

زُر `http://localhost:3000` وسجّل الدخول بالحساب الافتراضي `root / 123456`.

> لمزيد من تفاصيل النشر، راجع [📦 النشر](#-النشر)، ولتوثيق الواجهة راجع [📖 توثيق الواجهة](#-توثيق-الواجهة).

## ✨ أبرز المزايا

يُعدّ One Api Pro **بوابة AI API بمستوى المؤسسات**، مبنيًا من جديد بلغة Go + Vue 3، مع الحفاظ على كل وظائف النسخة الأصلية one-api، إلى جانب إعادة البناء على مستوى المعمارية والتحسينات بمستوى المؤسسات.

### 🖥️ لوحة التحكم المرئية

لوحة إدارة جديدة كليًا بتقنية Vue 3 + Arco Design، توفّر لوحة معلومات مرئية تعرض المؤشرات الأساسية واتجاهات الاستخدام وتوزيع استخدام النماذج بلمحة واحدة.

### 🧩 قدرات أساسية أخرى

- **دعم أكثر من 30 منصة نموذج**: تغطية شاملة للمنصات الرئيسية مثل OpenAI / Anthropic / Gemini / DeepSeek / Qwen / Wenxin / Xunfei / Zhipu، مع توحيدها خلف واجهة متوافقة مع OpenAI
- **حساب دقيق للتكلفة**: فوترة حسب Token أو حسب الدفعة، تسعير مستقل لـ Prompt / Completion / Cached، تراكب خصومات المجموعة، تتبّع الاستخدام الدوري

- **نظام صلاحيات متعدد المستويات**: أربعة مستويات Guest / User / Admin / Root، مع إصلاح ثغرة أذونات API النسخة الأصلية وتفصيل أدوات تحكم المشرف
- **أمان بمستوى المؤسسات**: HTTPS عبر المسار كامل، مصادقة Token، تقييد عناوين IP الفرعية، وتتبّع فوري لسجلات التدقيق

## 🔥 مقارنة One Api Pro مع one-api

| بُعد المقارنة | one-api | one-api-pro |
| --- | --- | --- |
| اسم المشروع | one-api | one-api-pro |
| معمارية Adaptor | إدارة مركزية للثوابت (56 سطرًا من `iota` في channeltype/define.go + مصفوفات متوازية في url.go + switch مزدوج الطبقات في helper.go)، وإضافة موفّر جديدة تتطلب تعديل 4 ملفات إطار | آلية تسجيل ذاتي (registry + register.go)، وإضافة موفّر يتطلب فقط إنشاء حزمة + تسجيل، مع صفر تعديلات على كود الإطار |
| دقة الصلاحيات | حدود غير واضحة بين المشرف والمستخدم العادي، ويمكن لأي شخص تعديل الإعدادات عبر API | نظام صلاحيات هرمي، يصلح ثغرة أذونات API، مع تفصيل أدوات تحكم المشرف |
| نمط الاشتراك | لا يوجد نظام باقة / اشتراك | باقة واشتراك كاملان + تقييد تردد دوري + تحكم حسب النموذج |
| الكتلة اللامركزية | لا دعم مستقل للكتلة، والنشر متعدد الأجهزة يتطلب مشاركة MySQL | دعم كتلة لامركزية متعددة النشاط، كل عقدة تملك MySQL + Redis مستقلتين، مع مزامنة عبر أحداث طبقة التطبيق لتحقيق الثقة دون قاعدة بيانات مشتركة |
| بنية الدليل | `relay/adaptor/` يسوّي 40 دليلًا، والبروتوكولات الأساسية والمزودون مختلطون معًا، ويتعارض `relay/model/` مع `model/` الجذري | `adaptor/openai/` و `adaptor/anthropic/` كبروتوكولات أساسية منفصلة، و `adaptor/provider/` يجمع 37 مزودًا، و `relay/schema/` يزيل تعارض الأسماء |
| لوحة الإدارة | 3 تنسيقات للواجهة الأمامية (default / berry / air) بوظائف إدارة أساسية | لوحة إدارة جديدة كليًا Vue 3 + Arco Design مع لوحة معلومات مرئية |
 | التحديث المستمر | توقف المشروع الأصلي عن التحديث في عام 2024 | صيانة وتحديث مستمران، مع تحسينات مخصصة لسيناريوهات المؤسسات |

## ⚙️ الإعدادات

النظام جاهز للاستخدام مباشرة دون إعداد.

يمكنك الإعداد عبر متغيرات البيئة أو وسائط سطر الأوامر؛ وبعد التشغيل، سجّل الدخول بحساب `root` إلى لوحة الإدارة لمتابعة الإعداد.

> **تلميح**: إذا لم تعرف معنى أحد الخيارات، يمكنك حذف قيمته مؤقتًا لرؤية نص الإرشادات الإضافي.

### 🔧 متغيرات البيئة

> يدعم One Api Pro قراءة متغيرات البيئة من ملف `.env`، راجع ملف `.env.example`، وعند الاستخدام أعد تسميته إلى `.env`. ويمكنك أيضًا تحديد مسار ملف الإعداد عبر وسيط `--env` (يدعم المسارات النسبية)، راجع قسم وسائط سطر الأوامر.

1. `REDIS_CONN_STRING`: عند تعيينه يُستخدم Redis كطبقة تخزين مؤقت.
   + مثال: `REDIS_CONN_STRING=redis://default:redispw@localhost:49153`
   + إذا كان زمن وصول قاعدة البيانات منخفضًا جدًا، فلا حاجة لتفعيل Redis؛ ويؤدي تفعيله إلى تأخر في البيانات.
   + إذا أردت استخدام وضع Sentinel أو الكتلة:
     + يجب تعيين هذا المتغير على قائمة العقد، مثل: `localhost:49153,localhost:49154,localhost:49155`.
     + بالإضافة إلى ذلك، يجب تعيين المتغيرات التالية:
       + `REDIS_PASSWORD`: كلمة المرور في وضع كتلة Redis أو Sentinel.
       + `REDIS_MASTER_NAME`: اسم العقدة الرئيسية في وضع Redis Sentinel.
2. `SESSION_SECRET`: عند تعيينه يُستخدم مفتاح جلسة ثابت، بحيث تبقى كوكيز المستخدمين الذين سجّلوا الدخول صالحة بعد إعادة تشغيل النظام.
   + مثال: `SESSION_SECRET=random_string`
3. `SQL_DSN`: عند تعيينه تُستخدم قاعدة البيانات المحددة بدلًا من SQLite؛ يُرجى استخدام MySQL أو PostgreSQL.
   + أمثلة:
     + MySQL: `SQL_DSN=root:123456@tcp(localhost:3306)/oneapi`
     + PostgreSQL: `SQL_DSN=postgres://postgres:123456@localhost:5432/oneapi` (قيد التكيّف، يُرحّب بالملاحظات)
   + لاحظ أنّه يجب إنشاء قاعدة البيانات `oneapi` مسبقًا، ولا حاجة لإنشاء الجداول يدويًا؛ ستنشئها البرنامج تلقائيًا.
   + إذا استخدمت قاعدة بيانات سحابية: إذا كان الخادم السحابي يتطلب التحقق من الهوية، يجب إضافة `?tls=skip-verify` إلى معلمات الاتصال.
   + يُرجى تعديل المعلمات التالية وفقًا لإعداد قاعدة البيانات (أو الإبقاء على القيم الافتراضية):
     + `SQL_MAX_IDLE_CONNS`: الحد الأقصى لعدد الاتصالات الخاملة، الافتراضي `100`.
     + `SQL_MAX_OPEN_CONNS`: الحد الأقصى لعدد الاتصالات المفتوحة، الافتراضي `1000`.
       + إذا ظهر الخطأ `Error 1040: Too many connections`، يرجى تقليل هذه القيمة.
     + `SQL_CONN_MAX_LIFETIME`: أقصى عمر للاتصال، الافتراضي `60`، بالدقائق.
4. `LOG_SQL_DSN`: عند تعيينه تُستخدم قاعدة بيانات مستقلة لجدول `logs`؛ يُرجى استخدام MySQL أو PostgreSQL.
5. `FRONTEND_BASE_URL`: عند تعيينه تُعاد توجيه طلبات الصفحات إلى العنوان المحدد؛ يُعيّن فقط من الخادم.
   + مثال: `FRONTEND_BASE_URL=https://openai.justsong.cn`
6. `MEMORY_CACHE_ENABLED`: تفعيل التخزين المؤقت في الذاكرة، ويسبب بعض التأخير في تحديث رصيد المستخدم؛ القيم الممكنة `true` و `false`، والافتراضي عند عدم التعيين `false`.
   + مثال: `MEMORY_CACHE_ENABLED=true`
7. `SYNC_FREQUENCY`: مزامنة الإعدادات مع قاعدة البيانات عند تفعيل التخزين المؤقت؛ الوحدة بالثواني، الافتراضي `600` ثانية.
   + مثال: `SYNC_FREQUENCY=60`
8. `NODE_TYPE`: يُحدد نوع العقدة عند تعيينه؛ القيم الممكنة `master` و `slave`، والافتراضي عند عدم التعيين `master`.
   + مثال: `NODE_TYPE=slave`
9. `CHANNEL_UPDATE_FREQUENCY`: تحديث رصيد القنوات بشكل دوري عند تعيينه؛ الوحدة بالدقائق، ولا يتم التحديث عند عدم التعيين.
   + مثال: `CHANNEL_UPDATE_FREQUENCY=1440`
10. `CHANNEL_TEST_FREQUENCY`: فحص القنوات بشكل دوري عند تعيينه؛ الوحدة بالدقائق، ولا يتم الفحص عند عدم التعيين.
    + مثال: `CHANNEL_TEST_FREQUENCY=1440`
11. `POLLING_INTERVAL`: الفاصل الزمني بين طلبات تحديث رصيد القنوات وفحص التوفر بشكل مجمّع؛ الوحدة بالثواني، الافتراضي بدون فاصل.
    + مثال: `POLLING_INTERVAL=5`
12. `BATCH_UPDATE_ENABLED`: تفعيل تجميع التحديثات المجمّعة لقاعدة البيانات، ويسبب بعض التأخير في تحديث رصيد المستخدم؛ القيم الممكنة `true` و `false`، والافتراضي عند عدم التعيين `false`.
    + مثال: `BATCH_UPDATE_ENABLED=true`
    + إذا واجهت مشكلة كثرة اتصالات قاعدة البيانات، يمكنك تجربة تفعيل هذا الخيار.
13. `BATCH_UPDATE_INTERVAL=5`: الفاصل الزمني لتجميع التحديثات المجمّعة؛ الوحدة بالثواني، الافتراضي `5`.
    + مثال: `BATCH_UPDATE_INTERVAL=5`
14. تقييد تردد الطلبات:
    + `GLOBAL_API_RATE_LIMIT`: حد معدل API العام (باستثناء طلبات الترحيل)، وهو أقصى عدد طلبات لكل عنوان IP خلال ثلاث دقائق، الافتراضي `180`.
    + `GLOBAL_WEB_RATE_LIMIT`: حد معدل الويب العام، وهو أقصى عدد طلبات لكل عنوان IP خلال ثلاث دقائق، الافتراضي `60`.
15. إعدادات ذاكرة الترميز:
    + `TIKTOKEN_CACHE_DIR`: ينزّل البرنامج عند التشغيل ترميزات الكلمات للنماذج العامة (مثل `gpt-3.5-turbo` و `gpt-4` و `gpt-4o`). إذا كانت الشبكة مقيدة أو غير متصلة، فعند انتهاء مهلة التنزيل (حوالي 30 ثانية) يتدهور تلقائيًا إلى عدّ تقريبي للرموز (حوالي `0.38 × عدد الأحرف`)، وتستمر الخدمة في العمل طبيعيًا. إذا أردت فوترة دقيقة، نزّل ملفات الترميز مسبقًا في بيئة متصلة إلى هذا الدليل، ثم انقلها إلى البيئة غير المتصلة.
    + `DATA_GYM_CACHE_DIR`: يعمل هذا الإعداد حاليًا بنفس دور `TIKTOKEN_CACHE_DIR`، لكن بأولوية أقل منه.
16. `RELAY_TIMEOUT`: إعداد مهلة الترحيل؛ الوحدة بالثواني، الافتراضي بدون تحديد مهلة.
17. `RELAY_PROXY`: عند تعيينه يُستخدم هذا الوكيل لطلب API.
18. `USER_CONTENT_REQUEST_TIMEOUT`: مهلة تنزيل المحتوى الذي يرفعه المستخدم؛ الوحدة بالثواني.
19. `USER_CONTENT_REQUEST_PROXY`: عند تعيينه يُستخدم هذا الوكيل لطلب المحتوى الذي يرفعه المستخدم، مثل الصور.
20. `SQLITE_BUSY_TIMEOUT`: مهلة انتظار قفل SQLite؛ الوحدة بالمللي ثانية، الافتراضي `3000`.
21. `GEMINI_SAFETY_SETTING`: إعداد الأمان في Gemini، الافتراضي `BLOCK_NONE`.
22. `GEMINI_VERSION`: إصدار Gemini الذي يستخدمه One Api Pro، الافتراضي `v1`.
23. `THEME`: إعداد تنسيق النظام، الافتراضي `default-pro` (لوحة إدارة Vue 3)، ويمكن أيضًا التبديل إلى `default` / `berry` / `air` (تنسيقات React القديمة)؛ راجع القيم الممكنة في [هذا الملف](../web/README.md).
24. `ENABLE_METRIC`: تعطيل القناة بناءً على معدل نجاح الطلبات؛ غير مفعّل افتراضيًا، والقيم الممكنة `true` و `false`.
25. `METRIC_QUEUE_SIZE`: حجم قائمة انتظار إحصاءات معدل نجاح الطلبات، الافتراضي `10`.
26. `METRIC_SUCCESS_RATE_THRESHOLD`: عتبة معدل نجاح الطلبات، الافتراضي `0.8`.
27. `INITIAL_ROOT_TOKEN`: إذا عيّنت هذه القيمة، فسوف ينشئ النظام تلقائيًا عند أول تشغيل رمز مستخدم root بقيمة هذا المتغير.
28. `INITIAL_ROOT_ACCESS_TOKEN`: إذا عيّنت هذه القيمة، فسوف ينشئ النظام تلقائيًا عند أول تشغيل رمز إدارة نظام للمستخدم root بقيمة هذا المتغير.
29. `ENFORCE_INCLUDE_USAGE`: فرض إرجاع `usage` في وضع البث (stream)؛ غير مفعّل افتراضيًا، والقيم الممكنة `true` و `false`.
30. `TEST_PROMPT`: موجه المستخدم عند اختبار النموذج، الافتراضي `Print your model name exactly and do not output without any other text.`.

#### 🌐 إعدادات الكتلة (نشر لامركزي متعدد النشاط)

> عندما لا تُعيّن المتغيرات التالية، يعمل النظام في وضع العقدة الواحدة دون أي تأثيرات جانبية.

1. `CLUSTER_ENABLED`: تفعيل وضع الكتلة؛ غير مفعّل افتراضيًا.
   + مثال: `CLUSTER_ENABLED=true`
2. `CLUSTER_NODE_ID`: رقم العقدة (1-49)، يجب أن يتطابق مع `auto_increment_offset` في MySQL، ولا يمكن تكراره بين العقد.
   + مثال: `CLUSTER_NODE_ID=1`
3. `CLUSTER_NODE_NAME`: اسم العقدة لسهولة التمييز، الافتراضي `node-{NODE_ID}`.
   + مثال: `CLUSTER_NODE_NAME=node-cn`
4. `CLUSTER_NODE_ADDRESS`: عنوان الوصول العام لهذه العقدة (يجب تضمين بادئة البروتوكول)، وتدفع العقد الأخرى البيانات عبر هذا العنوان.
   + مثال: `CLUSTER_NODE_ADDRESS=https://cn.example.com`
5. `CLUSTER_SECRET`: السر الأولي لهذه العقدة، **مستقل لكل عقدة**. يُكتب عند أول تشغيل كسر أولي إلى قاعدة البيانات، ويمكن تعديله لاحقًا بواسطة المشرف.
   + مثال: `CLUSTER_SECRET=MyClusterSecret123abc`
6. `CLUSTER_SEEDS`: عناوين العقد البذرة (مفصولة بفواصل)، تسجّل العقد الجديدة عند التشغيل لدى العقد البذرة للحصول على معلومات الكتلة؛ يكفي تعيين عقدة واحدة يمكن الوصول إليها. يمكن للعقدة الأولى عدم تعيينه أو تعيين عنوانها الخاص.
   + مثال: `CLUSTER_SEEDS=https://cn.example.com`
   + بذرات متعددة: `CLUSTER_SEEDS=https://cn.example.com,https://us.example.com`
7. `CLUSTER_PUSH_INTERVAL`: فاصل دفع مزامنة الأحداث؛ الوحدة بالثواني، الافتراضي `3`.
8. `CLUSTER_DISCOVERY_INTERVAL`: فاصل اكتشاف العقد؛ الوحدة بالثواني، تتنابذ العقد الحية كل دورة، الافتراضي `30`.
9. `CLUSTER_DEAD_PING_INTERVAL`: فاصل ping للعقد الفاشلة؛ الوحدة بالثواني، وهو أطول من فاصل العقد الحية لتقليل الطلبات غير الفعالة، الافتراضي `120`.
10. `CLUSTER_MAX_PING_FAILURES`: عدد مرات فشل ping المتتالية، وعند بلوغها تُعلَّم العقدة كفاشلة، الافتراضي `3`.
11. `CLUSTER_SYNC_LOGS`: هل تتم مزامنة جدول السجلات؛ حجم بيانات السجلات كبير ويمكن تعطيله عند الحاجة، الافتراضي `true`.
     + مثال: `CLUSTER_SYNC_LOGS=false`
12. `CLUSTER_BATCH_SIZE`: الحد الأقصى لعدد الأحداث في كل دفعة دفع، الافتراضي `50`.

### ⌨️ وسائط سطر الأوامر

1. `--port <port_number>`: تحديد رقم منفذ الاستماع للخادم، الافتراضي `3000`.
   + مثال: `--port 3000`
2. `--log-dir <log_dir>`: تحديد مجلد السجلات، وإذا لم يُحدد، يُحفظ افتراضيًا في مجلد `logs` داخل دليل العمل.
   + مثال: `--log-dir ./logs`
3. `--env <env_file_path>`: تحديد مسار ملف الإعداد، ويدعم المسارات النسبية والمطلقة. عند عدم التحديد، يُحمّل تلقائيًا ملف `.env` في الدليل الحالي.
   + مثال: `--env ./config.env`
   + مثال: `--env /etc/one-api-pro/production.env`
   + مثال لنشر متعدد الحالات:
     ```bash
     ./one-api-pro --env ./instances/instance1.env --port 3001 &
     ./one-api-pro --env ./instances/instance2.env --port 3002 &
     ```
   + أولوية الإعدادات: وسائط سطر الأوامر > متغيرات بيئة النظام > ملف الإعداد المحدد بـ `--env` > القيم الافتراضية
4. `--version`: طباعة رقم إصدار النظام والخروج.
   + مثال: `./one-api-pro --version`
   + مصادر رقم الإصدار (من الأعلى إلى الأدنى أولوية):
     1. ملف `VERSION` في دليل العمل الحالي أو بجوار الملف التنفيذي (يتوافق تلقائيًا مع وجود أو غياب سابقة `v`، مثل `0.0.2` أو `v0.0.2`)؛
     2. رقم الإصدار المحقون وقت البناء عبر `-ldflags "-X .../common.Version=..."` (يقوم `release.sh` و CI بحقنه تلقائيًا)؛
     3. القيمة الافتراضية في المصدر `common/constants.go`.
   + لذلك يكفي صيانة ملف `VERSION` في الجذر في موضع واحد، لتظل الأرقام المعروضة في `--version` وسجل التشغيل وواجهة `/api/status` ولوحة المعلومات الأمامية متسقة.
5. `--help`: عرض الاستخدام وشرح الوسائط.
   + مثال: `./one-api-pro --help`

### 🏢 النشر متعدد الأجهزة
1. اضبط `SESSION_SECRET` على نفس القيمة في جميع الخوادم.
2. يجب تعيين `SQL_DSN` لاستخدام قاعدة بيانات MySQL بدلًا من SQLite، وتتصل جميع الخوادم بنفس قاعدة البيانات.
3. يجب على جميع الخوادم الثانوية تعيين `NODE_TYPE` إلى `slave`؛ وإلا فإن الافتراضي هو خادم رئيسي.
4. بعد تعيين `SYNC_FREQUENCY`، ستزامن الخوادم الإعدادات من قاعدة البيانات دوريًا؛ عند استخدام قاعدة بيانات بعيدة، يُوصى بتعيين هذا الخيار وتفعيل Redis، سواء رئيسيًا أو ثانويًا.
5. يمكن للخوادم الثانوية اختياريًا تعيين `FRONTEND_BASE_URL` لإعادة توجيه طلبات الصفحات إلى الخادم الرئيسي.
6. ثبّت Redis **بشكل منفصل** على كل خادم ثانوي، وعيّن `REDIS_CONN_STRING`، بحيث يكون الوصول إلى قاعدة البيانات صفرًا ما لم تنتهِ صلاحية التخزين المؤقت؛ مما يقلل زمن الاستجابة (راجع شرح متغيرات البيئة لدعم كتلة Redis أو Sentinel).
7. إذا كان زمن وصول الخادم الرئيسي إلى قاعدة البيانات مرتفعًا أيضًا، فيجب أيضًا تفعيل Redis وتعيين `SYNC_FREQUENCY` لمزامنة الإعدادات من قاعدة البيانات دوريًا.

راجع [متغيرات البيئة](#-متغيرات-البيئة) لطريقة الاستخدام التفصيلية.

### 🌐 نشر الكتلة اللامركزية متعددة النشاط

يسمح وضع الكتلة لكل عقدة بنشر One Api Pro + MySQL مستقل، مع تحقيق الثقة المتبادلة في البيانات عبر مزامنة أحداث طبقة التطبيق، دون الحاجة إلى قاعدة بيانات مشتركة.

> **سيناريو التطبيق**: نشر في مناطق متعددة حول العالم، وصول أقرب لتقليل زمن الاستجابة، وتوافر عالٍ ومواجهة الكوارث، وموازنة تحميل متعددة العقد.

#### 🗺️ نظرة عامة على المعمارية

```
                    ┌─────────────┐
                    │  Nginx/LB   │  （统一入口，ip_hash 负载均衡）
                    └──────┬──────┘
                           │
            ┌──────────────┼──────────────┐
            │              │              │
     ┌──────┴──────┐ ┌────┴───────┐ ┌───┴────────┐
     │  Node A     │ │  Node B     │ │  Node C     │
     │ (one-api-pro)   │ │ (one-api-pro)   │ │ (one-api-pro)   │
     │ + MySQL     │ │ + MySQL     │ │ + MySQL     │
     │ + Redis     │ │ + Redis     │ │ + Redis     │
     └──────┬──────┘ └─────┬──────┘ └────┬────────┘
            │              │              │
            └────── HTTP 推送同步事件 ──────┘
```

#### ⭐ الخصائص الأساسية

- **اللامركزية**: جميع العقد متساوية، لا فرق بين رئيسي وثانوي، وأي تغيير بيانات في أي عقدة يُدفع بنشاط إلى جميع العقد الحية
- **أثر صفري**: التقاط تغييرات البيانات عبر استدعاءات GORM، دون تعديل كود الأعمال الحالي
- **دفع غير متزامن**: مزامنة البيانات لا تحجب التدفق الرئيسي، وتُدفع بشكل مجمّع عبر goroutine في الخلفية
- **حل التعارض**: مقارنة تعتمد على طابع زمني `updated_at`، وتُكتب البيانات الأحدث فقط
- **مزامنة تقييد التردد**: عدادات تزامن القنوات و RPM تُزامن عبر الجداول في قاعدة البيانات
- **توافق العقدة الواحدة**: عند عدم تعيين متغيرات الكتلة، يعمل النظام كليًا في وضع العقدة الواحدة

#### 📊 نطاق المزامنة

| جدول البيانات | هل يُزامن | شرح |
|--------|---------|------|
| users | ✅ | معلومات المستخدمين |
| tokens | ✅ | رموز API |
| channels | ✅ | إعدادات القنوات |
| abilities | ✅ | قدرات القنوات |
| options | ✅ | إعدادات النظام |
| redemptions | ✅ | أكواد الاستبدال |
| plans | ✅ | خطط الاشتراك |
| user_plans | ✅ | اشتراكات المستخدمين |
| plan_usages | ✅ | استخدام الخطة |
| channel_counters | ✅ | عدادات تقييد تردد القنوات |
| cluster_nodes | 🔄 Discovery | معلومات عقد الكتلة (تُحافَظ عبر آلية الاكتشاف، ولا تمر بمزامنة البيانات) |
| logs | ⚠️ اختياري | حجم بيانات السجلات كبير، يُتحكم فيه عبر `CLUSTER_SYNC_LOGS` |

#### 🚀 خطوات النشر

**1. إعداد MySQL (يجب أن تستخدم كل عقدة نسخة MySQL مستقلة)**

تحتاج كل عقدة إلى **قاعدة MySQL مستقلة** (لا يمكن إنشاء قواعد بيانات متعددة في نفس نسخة MySQL لنشر عقد متعددة، لأن `auto_increment_offset` متغير على مستوى النسخة).

```ini
# my.cnf للعقدة 1
[mysqld]
server-id = 1
auto_increment_increment = 50
auto_increment_offset = 1
log_bin = mysql-bin
binlog_format = ROW

# my.cnf للعقدة 2
[mysqld]
server-id = 2
auto_increment_increment = 50
auto_increment_offset = 2
log_bin = mysql-bin
binlog_format = ROW

# my.cnf للعقدة 3
[mysqld]
server-id = 3
auto_increment_increment = 50
auto_increment_offset = 3
log_bin = mysql-bin
binlog_format = ROW
```

> عند تعيين `auto_increment_increment` إلى 50، يدعم ذلك حتى 50 عقدة. يجب أن يتطابق `offset` لكل عقدة مع `CLUSTER_NODE_ID` ويكون مختلفًا عن غيره.

> **ملاحظة مهمة:** إنّ `auto_increment_increment` و `auto_increment_offset` هما متغيرات على **مستوى النسخة** في MySQL، وتؤثران على جميع قواعد البيانات داخل النسخة، ولا يمكن تعيين قيم مختلفة لقواعد بيانات مختلفة، ولا يمكن تعيينهما على مستوى الجدول (لا تدعم خيارات جداول MySQL إلا قيمة `AUTO_INCREMENT` البدائية، ولا تدعم الخطوة). لذلك يجب على كل عقدة **استخدام نسخة MySQL مستقلة**، ولا يمكن نشر عقد متعددة عبر إنشاء قواعد بيانات مختلفة داخل نفس نسخة MySQL. لتشغيل عدة نسخ MySQL على نفس الجهاز، يمكنك تشغيل عدة عمليات mysqld على منافذ مختلفة، أو استخدام Docker لتشغيل عدة حاويات MySQL مستقلة.

> **بخصوص `server-id` و binlog:** يجب أن يكون `server-id` مختلفًا بين جميع نسخ MySQL في نفس الكتلة. ويُوصى بشدة بتفعيل `log_bin` و `binlog_format=ROW` — فهي تُستخدم للتوسعة المستقبلية للنسخ المتماثل رئيسي-ثانوي والاسترداد النقطي الزمني. مزامنة بيانات الكتلة نفسها لا تعتمد على binlog (تُنفَّذ عبر استدعاءات GORM في طبقة التطبيق)، لكن binlog يوفر ضمانًا إضافيًا للاعتمادية.

**2. إعداد Redis (يجب أن تستخدم كل عقدة نسخة Redis مستقلة)**

**6. ترتيب التشغيل**

1. شغّل العقدة الأولى (Node A)، واترك `CLUSTER_SEEDS` فارغًا أو ضع عنوانها الخاص
2. انتظر حتى تكتمل إقلاع Node A تمامًا (حوالي 5-10 ثوانٍ، ولاحظ سجل «اكتمل تهيئة وحدة الكتلة»)
3. شغّل العقد اللاحقة، وضع في `CLUSTER_SEEDS` عنوان أي عقدة حية
4. بعد إقلاع العقد اللاحقة، ستعمل ping تلقائيًا على العقد البذرة، وتكتشف جميع العقد الأخرى بأسلوب انتقالي
5. بعد إقلاع جميع العقد، يمكنك عرض حالة العقد عبر صفحة «الإعدادات → إدارة العقد» في لوحة إدارة أي عقدة

**7. مثال على إعداد موازنة تحميل Nginx (اختياري)**

```nginx
upstream one_api_cluster {
    ip_hash;  # تجزئة مضيفة قائمة على عنوان IP، ويُثبَّت طلب المستخدم نفسه على نفس العقدة لضمان إصابة session/cache
    server cn.example.com:3000;
    server us.example.com:3000;
    server eu.example.com:3000;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://one_api_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

> **استخدام `ip_hash` أمر بالغ الأهمية**: يضمن وصول طلبات نفس المستخدم دائمًا إلى نفس العقدة، لتجنّب فقدان حالات تقييد تردد الخطة وذاكرة Redis في العقد المتعددة.

#### ⚠️ ملاحظات مهمة

- يجب أن تملك كل عقدة نسخ MySQL و Redis مستقلة، دون مشاركة قاعدة بيانات
- يجب أن يكون `CLUSTER_SECRET` متطابقًا في جميع العقد؛ استخدم كلمة مرور قوية واحفظها جيدًا
- يجب أن يكون `CLUSTER_NODE_ID` مختلفًا بين جميع العقد، ومتطابقًا مع `auto_increment_offset` في MySQL
- يجب أن يكون `CLUSTER_NODE_ADDRESS` عنوانًا عامًا يمكن للعقد الأخرى الوصول إليه (يتضمن بادئة البروتوكول مثل `https://`)
- يجب إتمام تهيئة البيانات قبل إطلاق عقدة جديدة يدويًا (سحب لقطة من عقدة متصلة)
- حجم بيانات جدول السجلات (logs) كبير، ويمكن إيقاف مزامنة السجلات عبر `CLUSTER_SYNC_LOGS=false`
- يجب أن تتطابق `auto_increment_increment` و `auto_increment_offset` في MySQL مع إعداد `CLUSTER_NODE_ID`
- يعتمد اكتشاف العقد آلية تسجيل ping ثنائية الاتجاه، ولا تُحذف العقد الفاشلة بل تُعلَّم فقط على status=2، وتعود تلقائيًا بعد استعادة الشبكة
- `CLUSTER_SEEDS` هو مجرد توجيه لأول تشغيل؛ بمجرد اكتشاف العقد الأخرى عبر ping، لن يعود النظام معتمدًا على SEEDS
- التغييرات التي تحدثها العقد الأخرى أثناء انقطاع العقدة **لا تُرسل تلقائيًا لاحقًا**، وعند إعادة العقدة غير المتصلة للاتصال يلزم سحب لقطة لملء البيانات

#### 📝 حول «التسجيل الذاتي» للعقدة المحلية

عند إقلاع كل عقدة، تُكتب سجلًا محليًا في جدول `cluster_nodes` الخاص بها (`node_id` يساوي `CLUSTER_NODE_ID` المكوّن لها). هذا **تصميم مقصود**، للأسباب التالية:

1. **العرض في لوحة الإدارة**: في صفحة «الإعدادات → إدارة العقد»، يحتاج المشرف إلى رؤية معلومات هذه العقدة (العنوان، الحالة، وقت نبضات القلب) لتشخيص المشكلات
2. **الانتقالية في اكتشاف العقد**: عندما تستقبل العقدة B طلب ping من العقدة A، تُعيد A في الاستجابة قائمة العقد الكاملة (متضمنةً A نفسها). عند استلامها تدمجها B في جدولها المحلي. وهكذا يمكن لـ C أن تتعلم بوجود A عبر استجابة B
3. **أساس الحكم على البقاء**: يُحدَّث `last_heartbeat` للسجل المحلي تلقائيًا كل 30 ثانية (في دالة `discoverOnce`)، مما يعكس حالة التشغيل الطبيعي لهذه العقدة

**التسجيل الذاتي لا يسبب مزامنة بيانات دائرية.** يوفر النظام الحماية على 5 مستويات:

| نقطة الحماية | الدور |
|---|---|
| ① فلتر SQL لـ `GetAllRemoteNodes` | عند الاكتشاف يضيف SQL شرط `node_id != ?` لاستبعاد العقدة المحلية |
| ② فلتر SQL لـ `GetAliveNodesForSync` | عند الدفع يضيف SQL شرط `node_id != ?` لاستبعاد العقدة المحلية |
| ③ `handlePing` يرفض ping الذاتي | يرفض صراحةً `req.NodeId == NodeID` |
| ④ `mergeDiscoveredNodes` يتجاوز العقدة المحلية | عند دمج العقد المكتشفة يتجاوز العقدة المحلية |
| ⑤ `ApplyEvents` يتجاوز أحداث العقدة المحلية | عند تطبيق الأحداث يتجاوز الأحداث الناتجة عن العقدة المحلية |

تدفق البيانات أحادي الاتجاه: من العقدة المحلية إلى البعيدة، ومن البعيدة سحبًا وتطبيقًا إلى المحلية، **لا يوجد أبدًا حلقة مغلقة**.

تعرض لوحة الإدارة شارة «محلية» زرقاء بجوار اسم العقدة المحلية، وتُعطّل عمليتي «حذف» و«ping يدوي» على هذه العقدة (لا معنى لهما للعقدة المحلية).

#### 🔐 حول «سر مستقل لكل عقدة»

تملك كل عقدة **سرّها الخاص**، ولا تُستخدم بعد الآن سرًا مشتركًا عالميًا. أسباب التصميم:

1. **الأمان**: تسريب سر من عقدة لا يؤثر على العقد الأخرى
2. **مرونة الإدارة**: يمكن لكل عقدة تدوير سرّها الخاص بشكل مستقل
3. **الاكتشاف التلقائي**: عند ping بين العقد تحمل تلقائيًا سرّها الخاص ليحفظه الطرف المقابل

**دورة حياة السر**:
- أول إقلاع للعقدة: استخدم متغير البيئة `CLUSTER_SECRET` كقيمة أولية، واكتبها في حقل `cluster_nodes.secret_key`
- الإقلاعات اللاحقة: اقرأ من `cluster_nodes.secret_key`
- يمكن للمشرف تعديل سر أي عقدة أخرى من صفحة «إدارة العقد»
- عند ping، رأس `X-Cluster-Secret` = سرّ **العقدة الهدف** (تُستحضر من قاعدة البيانات المحلية)

**إجراء إضافة عقدة جديدة**:
1. أضِف على العقدة A سجل العقدة B، وملأها بقيمة `CLUSTER_SECRET` الخاصة بـ B
2. أضِف على العقدة B سجل العقدة A، وملأها بقيمة `CLUSTER_SECRET` الخاصة بـ A
3. ترسل A ping إلى B: باستخدام سرّ B؛ وتستقبل B: تتحقق من سرّها الخاص ✓
4. تحمل استجابة B سرّي A و B كلاهما، فتُحدِّث A ما حفظته محليًا

#### 🗑️ حول «الحذف الناعم» للعقد

عندما يحذف المشرف عقدة، **لا يُحذف السجل فعليًا**، بل يُعيّن `disabled = true`:

- يمنع العقدة المحذوفة من «العودة تلقائيًا» (آلية ping تعيد تسجيلها)
- تظل العقد المعطّلة تستجيب لـ ping (لإعلام الطرف الآخر بأنها متصلة)، ولكنها لن تحصل على معلومات هذه العقدة
- الحذف الفعلي يتطلب SQL يدوي: `DELETE FROM cluster_nodes WHERE node_id = ?`

#### 🔄 حول «آلية مزامنة البيانات» (مهم)

تعتمد **مزامنة بيانات الكتلة** كليًا على آلية **أحداث GORM + الدفع النشط عبر HTTP**:
- أي عملية INSERT/UPDATE/DELETE على جدول أعمال → يلتقطها استدعاء GORM → تُكتب في جدول `sync_events` → يدفعها goroutine Pusher إلى جميع العقد الحية
- يكتب الطرف المستلم عبر `WithSkipHook` إلى قاعدة البيانات المحلية (لا يحدث تراجع دائري)
- يتجاهل الطرف المستلم الأحداث التي يكون `event.NodeId == NodeID` للعقدة المحلية (ضمان مزدوج)

**مقارنة معمارية**: هذا التصميم **لا ينفّذ سحبًا نشطًا عبر العقد**، للأسباب التالية:
1. **اقتحام الأعمال**: يتطلب السحب عبر العقد معرفة الحقول الفريدة لكل جدول أعمال، مما يقتحم كود الأعمال
2. **تعارض المفاتيح الأساسية**: معرّفات الزيادة الذاتية عبر العقد غير متتابعة (بفعل اختلاف `auto_increment_offset`)، واستخدام معرّف العقدة المصدر يكسر تصميم offset
3. **تعقيد مرتفع**: تكلفة الصيانة عالية، والتحسن في الاعتمادية محدود
4. **الدفع النشط كافٍ**: تغطي الدفعات 95% من السيناريوهات (المزامنة العادية عندما تكون العقد متصلة)

**قيود معروفة ومتطلبات التشغيل**:
- التغييرات التي تحدثها العقد الأخرى أثناء انقطاع العقدة → **تُفقد نهائيًا** (الدفع فوري فقط)
- بعد إعادة اتصال العقدة، لا يمكنها تلقائيًا ملء بيانات فترة الانقطاع
- العقد الجديدة تستقبل فقط التغييرات بعد انضمامها، ولا بيانات تاريخية
- **العلاج التشغيلي**: استخدم `mysqldump` للتصدير من عقدة أخرى ثم الاستيراد

**مقارنة سيناريوهات النشر النموذجية**:

| السيناريو | هل يلزم السحب | طريقة المعالجة |
|---|---|---|
| العقدة متصلة دائمًا | ❌ | الدفع كافٍ تمامًا |
| العقدة تعيد التشغيل أحيانًا (بالمستوى الدقيق) | ⚠️ | فقدان بيانات قصير أثناء الانقطاع، مقبول تشغيليًا |
| صيانة متكررة للعقدة | ❌ | يستمر الدفع، وتُستأنف فورًا بعد إعادة التشغيل |
| عقدة جديدة تنضم للكتلة | ❌ | يهيئها DBA يدويًا عبر `mysqldump` |
| عقدة منقطعة طويلًا تتعافى | ❌ | يصلحها DBA يدويًا عبر `mysqldump` |

إذا ظهرت صفحة بيضاء عند الوصول بعد النشر، راجع [#97](https://github.com/modelbus/one-api-pro/issues/97).
