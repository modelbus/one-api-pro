## 🚀 Быстрый старт

### 1. Получить исполняемый файл

Скачайте предварительно собранную версию со страницы [GitHub Releases](https://github.com/modelbus/one-api-pro/releases/latest) или соберите из исходного кода:

```bash
git clone https://github.com/modelbus/one-api-pro.git
cd one-api-pro
```

### 2. (Сборка из исходников) Собрать фронтенд Vue 3

```bash
cd web
sh build.sh        # собирает все темы из web/THEMES (по умолчанию default-pro)
cd ..
```

### 3. (Сборка из исходников) Собрать бэкенд

> Бэкенд должен компилироваться **после** сборки фронтенда, чтобы встроить самые свежие ресурсы фронтенда.

```bash
go build -ldflags "-s -w" -o one-api-pro
```

### 4. (Опционально) Однокнопочная сборка для нескольких платформ

Используйте скрипт `release.sh` в корне репозитория, чтобы одной командой загрузить зависимости, собрать фронтенд и выполнить кросс-компиляцию для всех платформ:

```bash
./release.sh                          # использовать файл VERSION как номер версии
./release.sh v0.1.0                   # указать номер версии
./release.sh v0.1.0 --skip-frontend   # пропустить сборку фронтенда (переиспользовать web/build)
```

> Предварительные зависимости: `go`, `node`, `npm`. Номер версии берётся из файла `VERSION` в корне (автоматически совместимо с наличием или отсутствием префикса `v`).

Результат сборки — **статически слинкованный «голый» исполняемый файл** (без распаковки, запускается напрямую), который выводится в каталог `dist/`:

```
dist/one-api-pro-linux-amd64
dist/one-api-pro-linux-arm64
dist/one-api-pro-windows-amd64.exe
dist/one-api-pro-darwin-amd64
dist/one-api-pro-darwin-arm64
```

> Файлы `linux-*` — статически слинкованные, подходят для CentOS и Ubuntu. GitHub Releases автоматически собираются и публикуются файлом `.github/workflows/release.yml` при пуше тега `v*`, логика вывода идентична локальному `release.sh`.

### 5. Запуск

```bash
./one-api-pro --port 3000 --log-dir ./logs
```

Откройте `http://localhost:3000` и войдите с начальной учётной записью `root / 123456`.

> Подробное развертывание описано в разделе [📦 Развертывание](#-развертывание), документация API — в разделе [📖 Документация API](#-документация-api).

## ✨ Ключевые возможности

One Api Pro — это **корпоративный AI API Gateway**, созданный на Go + Vue 3. Сохраняя все функции оригинального one-api, он получил архитектурную переработку и корпоративные улучшения.

### 🖥️ Визуальная панель управления

Совершенно новая админ-панель на Vue 3 + Arco Design с панелью визуализации данных: ключевые метрики, тренды использования и распределение по моделям — всё с первого взгляда.

|:---:|:---:|
| ![Панель управления](../docs/Demo-Index.png) | ![Панель управления](../docs/Demo-Index.png) |

### 🔑 Тонкое управление токенами

Многомерное управление токенами: белые списки доступных моделей, ограничения по IP-подсетям, лимит квоты, срок действия, безлимитная квота. Детализация прав вплоть до отдельной модели.

| Управление токенами |

| ![Управление токенами](../docs/Demo-Token.png) |

### 📦 Система тарифов и подписок

Полноценная система тарифов и подписок: тарификация по токенам / по запросам, периодическое ограничение частоты (час / неделя / месяц), тонкое управление по моделям, поддержка рекомендуемых тарифов и настройки цен.

### 💳 Заказы и реальные платежи

Каждое оформление тарифа оставляет **полную запись аудита заказа** (номер заказа, пользователь, JSON-снимок тарифа, сумма, способ оплаты, статус, время оплаты, номер транзакции канала). Поддерживаются два типа заказов — тариф и пополнение. Нативно интегрированы **WeChat Pay Native** (QR-код на ПК) и **Alipay Face-to-Face** (TradePrecreate), а также предустановлены банковский / офлайн / бесплатный каналы для стороны администратора. Доплата при апгрейде тарифа рассчитывается автоматически пропорционально оставшимся дням; в режиме наложения старый и новый тарифы действуют параллельно. Все правила можно оперативно переключать на вкладке «План» в разделе «Операции».

Поддержка децентрализованного мультиактивного кластерного развертывания: каждый узел — независимые MySQL + Redis. Синхронизация данных через события уровня приложения, без общей базы данных, что естественно поддерживает низкую задержку при обращении из любого региона.

### 🧩 Другие ключевые возможности

- **Подключение 30+ модельных платформ** — полный охват OpenAI / Anthropic / Gemini / DeepSeek / Qwen / Wenxin / iFlytek / Zhipu и других популярных платформ, единый OpenAI-совместимый интерфейс
- **Точный расчет себестоимости** — тарификация по токенам или по числу запросов, независимые цены Prompt / Completion / Cached, накладывающиеся групповые скидки, отслеживание расхода за период
- **Балансировка нагрузки каналов** — случайное распределение по весам, автоматическое переключение при сбоях, политики охлаждения / отключения, ограничение конкурентности каналов и RPM
- **Многоуровневая система прав** — четыре уровня Guest / User / Admin / Root, исправлена уязвимость прав доступа к API в оригинальной версии, детализированное управление правами администратора
- **Корпоративная безопасность** — HTTPS по всему пути, аутентификация токенов, ограничения по IP-подсетям, журналы аудита в реальном времени

## 🔥 Сравнение с one-api

| Критерий сравнения | one-api | one-api-pro |
| --- | --- | --- |
| Название проекта | one-api | one-api-pro |
| Архитектура Adaptor | Централизованное управление константами (channeltype/define.go 56 строк iota + параллельные массивы в url.go + двухуровневый switch в helper.go); добавление нового провайдера требует правки 4 файлов фреймворка | Механизм саморегистрации (registry + register.go); для добавления провайдера достаточно создать пакет + зарегистрировать его, правки кода фреймворка не требуются |
| Детализация прав | Размытые границы прав администратора и обычного пользователя, любой может менять настройки через API | Уровневая система прав, исправлена уязвимость прав доступа к API, детализированное управление правами администратора |
| Модель подписки | Нет системы тарифов / подписок | Полная система тарифов и подписок + периодические лимиты частоты + управление по моделям |
| Децентрализованный кластер | Отдельной поддержки кластера нет, многомашинное развертывание требует общей MySQL | Поддержка децентрализованного мультиактивного кластера: каждый узел — свои MySQL + Redis, синхронизация через события уровня приложения, без общей базы данных |
| Структура каталогов | relay/adaptor/ — 40 разложенных каталогов, базовые протоколы смешаны с провайдерами; relay/model/ конфликтует с корневым model/ | adaptor/openai/, adaptor/anthropic/ как базовые протоколы, вынесены отдельно; adaptor/provider/ объединяет 37 провайдеров; relay/schema/ устраняет конфликт имен |
| Админ-панель | 3 темы фронтенда (default/berry/air), базовые функции управления | Совершенно новая админ-панель на Vue 3 + Arco Design с визуальной панелью управления |
| Постоянное обновление | Оригинальный проект остановлен в 2024 году | Активная поддержка и обновление, оптимизация под корпоративные сценарии |

## ⚙️ Конфигурация

Система работает сразу после установки (out of the box).

Вы можете настроить её через переменные окружения или аргументы командной строки; после запуска войдите под пользователем `root` и продолжите настройку в админ-панели.

> **Подсказка**: если вы не знаете значения какого-либо параметра, временно удалите его значение, чтобы увидеть дополнительные подсказки.

### 🔧 Переменные окружения

> One Api Pro поддерживает чтение переменных окружения из файла `.env`. Смотрите файл `.env.example`; при использовании переименуйте его в `.env`. Также можно указать путь к файлу конфигурации через параметр `--env` (поддерживаются относительные пути), подробнее в разделе об аргументах командной строки.

1. `REDIS_CONN_STRING` — если задано, Redis используется как кэш.
   + Пример: `REDIS_CONN_STRING=redis://default:redispw@localhost:49153`
   + Если задержка обращения к базе данных низкая, включать Redis не обязательно — после включения может возникнуть проблема устаревания данных.
   + Если нужно использовать Sentinel или кластерный режим:
     + Необходимо задать переменную окружения как список узлов, например: `localhost:49153,localhost:49154,localhost:49155`.
     + Кроме того, нужно задать следующие переменные окружения:
       + `REDIS_PASSWORD` — пароль в режиме кластера Redis или Sentinel.
       + `REDIS_MASTER_NAME` — имя главного узла в режиме Sentinel.
2. `SESSION_SECRET` — если задано, используется фиксированный секрет сессии, поэтому после перезапуска системы cookie уже вошедших пользователей остаются действительными.
   + Пример: `SESSION_SECRET=random_string`
3. `SQL_DSN` — если задано, используется указанная база данных вместо SQLite. Используйте MySQL или PostgreSQL.
   + Примеры:
     + MySQL: `SQL_DSN=root:123456@tcp(localhost:3306)/oneapi`
     + PostgreSQL: `SQL_DSN=postgres://postgres:123456@localhost:5432/oneapi` (в процессе разработки, приветствуется обратная связь)
   + Обратите внимание: базу данных `oneapi` нужно создать заранее; таблицы создаются автоматически при первом запуске.
   + При использовании облачной базы данных: если облачный сервер требует проверки личности, добавьте в строку подключения `?tls=skip-verify`.
   + Настройте следующие параметры в соответствии с вашей конфигурацией базы данных (или оставьте значения по умолчанию):
     + `SQL_MAX_IDLE_CONNS` — максимальное число простаивающих соединений, по умолчанию `100`.
     + `SQL_MAX_OPEN_CONNS` — максимальное число открытых соединений, по умолчанию `1000`.
       + При ошибке `Error 1040: Too many connections` уменьшите это значение.
     + `SQL_CONN_MAX_LIFETIME` — максимальное время жизни соединения, по умолчанию `60` минут.
4. `LOG_SQL_DSN` — если задано, для таблицы `logs` используется отдельная база данных. Используйте MySQL или PostgreSQL.
5. `FRONTEND_BASE_URL` — если задано, запросы страниц перенаправляются на указанный адрес. Допустима настройка только на сервере.
   + Пример: `FRONTEND_BASE_URL=https://openai.justsong.cn`
6. `MEMORY_CACHE_ENABLED` — включает кэширование в памяти, что приводит к некоторой задержке обновления квоты пользователя. Допустимые значения `true` и `false`; при отсутствии по умолчанию `false`.
   + Пример: `MEMORY_CACHE_ENABLED=true`
7. `SYNC_FREQUENCY` — частота синхронизации конфигурации с базой данных при включённом кэшировании, в секундах, по умолчанию `600` секунд.
   + Пример: `SYNC_FREQUENCY=60`
8. `NODE_TYPE` — задаёт тип узла. Допустимые значения `master` и `slave`; при отсутствии по умолчанию `master`.
   + Пример: `NODE_TYPE=slave`
9. `CHANNEL_UPDATE_FREQUENCY` — если задано, периодически обновляет баланс каналов, в минутах; при отсутствии обновление не выполняется.
   + Пример: `CHANNEL_UPDATE_FREQUENCY=1440`
10. `CHANNEL_TEST_FREQUENCY` — если задано, периодически проверяет каналы, в минутах; при отсутствии проверка не выполняется.
    + Пример: `CHANNEL_TEST_FREQUENCY=1440`
11. `POLLING_INTERVAL` — интервал между запросами при пакетном обновлении баланса каналов и проверке доступности, в секундах; по умолчанию интервала нет.
    + Пример: `POLLING_INTERVAL=5`
12. `BATCH_UPDATE_ENABLED` — включает пакетное агрегированное обновление базы данных, что приводит к некоторой задержке обновления квоты пользователя. Допустимые значения `true` и `false`; при отсутствии по умолчанию `false`.
    + Пример: `BATCH_UPDATE_ENABLED=true`
    + Если вы столкнулись со слишком большим числом соединений с базой данных, попробуйте включить эту опцию.
13. `BATCH_UPDATE_INTERVAL=5` — интервал агрегирования пакетного обновления, в секундах, по умолчанию `5`.
    + Пример: `BATCH_UPDATE_INTERVAL=5`
14. Ограничение частоты запросов:
    + `GLOBAL_API_RATE_LIMIT` — глобальное ограничение частоты API (кроме проксируемых запросов), максимальное число запросов с одного IP за три минуты, по умолчанию `180`.
    + `GLOBAL_WEB_RATE_LIMIT` — глобальное ограничение частоты Web, максимальное число запросов с одного IP за три минуты, по умолчанию `60`.
15. Настройки кэша кодировщика:
    + `TIKTOKEN_CACHE_DIR` — при запуске программы автоматически загружаются кодировки токенов обычных моделей (например, `gpt-3.5-turbo`, `gpt-4`, `gpt-4o`). При ограниченном или отсутствующем доступе к сети по истечении таймаута загрузки (около 30 секунд) автоматически выполняется переход к приблизительному подсчёту токенов (около `0.38 × число символов`), и сервис всё равно нормально запускается. Для точной тарификации предварительно загрузите файлы кодировок в этот каталог в среде с доступом в интернет, а затем перенесите их в офлайн-среду.
    + `DATA_GYM_CACHE_DIR` — сейчас назначение этой конфигурации совпадает с `TIKTOKEN_CACHE_DIR`, но приоритет у неё ниже.
16. `RELAY_TIMEOUT` — таймаут проксирования (relay), в секундах; по умолчанию таймаут не задан.
17. `RELAY_PROXY` — если задано, для обращения к API используется этот прокси.
18. `USER_CONTENT_REQUEST_TIMEOUT` — таймаут загрузки пользовательского контента, в секундах.
19. `USER_CONTENT_REQUEST_PROXY` — если задано, для обращения к пользовательскому контенту (например, изображениям) используется этот прокси.
20. `SQLITE_BUSY_TIMEOUT` — таймаут ожидания блокировки SQLite, в миллисекундах, по умолчанию `3000`.
21. `GEMINI_SAFETY_SETTING` — настройки безопасности Gemini, по умолчанию `BLOCK_NONE`.
22. `GEMINI_VERSION` — версия Gemini, используемая One Api Pro, по умолчанию `v1`.
23. `THEME` — тема системы, по умолчанию `default-pro` (админ-панель Vue 3); также можно переключить на `default` / `berry` / `air` (старые темы React). Допустимые значения указаны [здесь](../web/README.md).
24. `ENABLE_METRIC` — отключать ли каналы по проценту успешных запросов, по умолчанию выключено. Допустимые значения `true` и `false`.
25. `METRIC_QUEUE_SIZE` — размер очереди статистики процента успешных запросов, по умолчанию `10`.
26. `METRIC_SUCCESS_RATE_THRESHOLD` — порог процента успешных запросов, по умолчанию `0.8`.
27. `INITIAL_ROOT_TOKEN` — если задано, при первом запуске системы автоматически создаётся токен пользователя root со значением этой переменной окружения.
28. `INITIAL_ROOT_ACCESS_TOKEN` — если задано, при первом запуске системы автоматически создаётся системный токен доступа (Access Token) пользователя root со значением этой переменной окружения.
29. `ENFORCE_INCLUDE_USAGE` — принудительно возвращать `usage` в потоковом режиме (stream), по умолчанию выключено. Допустимые значения `true` и `false`.
30. `TEST_PROMPT` — пользовательский prompt при тестировании моделей, по умолчанию `Print your model name exactly and do not output without any other text.`.

#### 🌐 Конфигурация кластера (децентрализованное мультиактивное развертывание)

> Если не заданы следующие переменные окружения, система работает в режиме одного узла, без каких-либо побочных эффектов.

1. `CLUSTER_ENABLED` — включает ли кластерный режим, по умолчанию выключено.
   + Пример: `CLUSTER_ENABLED=true`
2. `CLUSTER_NODE_ID` — номер узла (1–49). Должен совпадать с `auto_increment_offset` MySQL; у разных узлов не может быть одинаковым.
   + Пример: `CLUSTER_NODE_ID=1`
3. `CLUSTER_NODE_NAME` — имя узла для удобного распознавания, по умолчанию `node-{NODE_ID}`.
   + Пример: `CLUSTER_NODE_NAME=node-cn`
4. `CLUSTER_NODE_ADDRESS` — публичный адрес доступа к данному узлу (должен включать префикс протокола); другие узлы используют этот адрес для отправки данных.
   + Пример: `CLUSTER_NODE_ADDRESS=https://cn.example.com`
5. `CLUSTER_SECRET` — начальный секрет данного узла, **на каждом узле свой**. При первом запуске записывается в базу данных как начальный секрет, позднее может быть изменён admin.
   + Пример: `CLUSTER_SECRET=MyClusterSecret123abc`
6. `CLUSTER_SEEDS` — адреса узлов-«семян» (через запятую); при запуске новый узел регистрируется у «семени», чтобы получить информацию о кластере. Достаточно указать один доступный узел. Первый узел можно не указывать или указать свой собственный адрес.
   + Пример: `CLUSTER_SEEDS=https://cn.example.com`
   + Несколько «семян»: `CLUSTER_SEEDS=https://cn.example.com,https://us.example.com`
7. `CLUSTER_PUSH_INTERVAL` — интервал отправки событий синхронизации, в секундах, по умолчанию `3`.
8. `CLUSTER_DISCOVERY_INTERVAL` — интервал обнаружения узлов, в секундах; живые узлы пингуют друг друга каждый цикл, по умолчанию `30`.
9. `CLUSTER_DEAD_PING_INTERVAL` — интервал пинга отказавших узлов, в секундах; больше интервала живых узлов, чтобы уменьшить количество бесполезных запросов, по умолчанию `120`.
10. `CLUSTER_MAX_PING_FAILURES` — количество последовательных неудачных пингов, после которого узел помечается как отказавший, по умолчанию `3`.
11. `CLUSTER_SYNC_LOGS` — синхронизировать ли таблицу журналов; при большом объёме данных журналов можно отключить, по умолчанию `true`.
     + Пример: `CLUSTER_SYNC_LOGS=false`
12. `CLUSTER_BATCH_SIZE` — максимальное число событий за одну отправку, по умолчанию `50`.

### ⌨️ Аргументы командной строки

1. `--port <port_number>` — задаёт номер порта для прослушивания сервером, по умолчанию `3000`.
   + Пример: `--port 3000`
2. `--log-dir <log_dir>` — задаёт каталог журналов; если не задан, по умолчанию сохраняется в папку `logs` в рабочем каталоге.
   + Пример: `--log-dir ./logs`
3. `--env <env_file_path>` — задаёт путь к файлу конфигурации; поддерживаются относительные и абсолютные пути. Если не задан, автоматически загружается файл `.env` из текущего каталога.
   + Пример: `--env ./config.env`
   + Пример: `--env /etc/one-api-pro/production.env`
   + Пример развертывания нескольких экземпляров:
     ```bash
     ./one-api-pro --env ./instances/instance1.env --port 3001 &
     ./one-api-pro --env ./instances/instance2.env --port 3002 &
     ```
   + Приоритет конфигурации: аргументы командной строки > переменные окружения системы > файл конфигурации, заданный через `--env` > значения по умолчанию
4. `--version` — печатает номер версии системы и завершает работу.
   + Пример: `./one-api-pro --version`
   + Источник номера версии (приоритет от высокого к низкому):
     1. Файл `VERSION` в текущем рабочем каталоге или в одном каталоге с исполняемым файлом (автоматически совместимо с наличием или отсутствием префикса `v`, например `0.0.2` или `v0.0.2`);
     2. Номер версии, внедрённый при сборке через `-ldflags "-X .../common.Version=..."` (`release.sh` и CI внедряют его автоматически);
     3. Значение по умолчанию в исходном коде `common/constants.go`.
   + Поэтому достаточно поддерживать файл `VERSION` в корне — тогда `--version`, лог запуска, интерфейс `/api/status` и версия на панели управления фронтенда останутся согласованными.
5. `--help` — показывает справку по использованию и описание параметров.
   + Пример: `./one-api-pro --help`

### 🏢 Многомашинное развертывание
1. На всех серверах задайте одинаковое значение `SESSION_SECRET`.
2. Обязательно укажите `SQL_DSN`, используйте базу данных MySQL вместо SQLite; все серверы подключаются к одной и той же базе данных.
3. На всех подчинённых серверах необходимо задать `NODE_TYPE` как `slave`; если не задан, по умолчанию узел считается главным.
4. После установки `SYNC_FREQUENCY` сервер будет периодически синхронизировать конфигурацию из базы данных. При использовании удалённой базы данных рекомендуется задать этот параметр и включить Redis — независимо от того, главный это сервер или подчинённый.
5. На подчинённых серверах можно при желании задать `FRONTEND_BASE_URL`, чтобы перенаправлять запросы страниц на главный сервер.
6. Установите Redis **отдельно** на каждом подчинённом сервере и задайте `REDIS_CONN_STRING`. Это позволяет не обращаться к базе данных, пока кэш не устарел, снижая задержку (поддержку кластера или режима Sentinel см. в описании переменных окружения).
7. Если задержка обращения к базе данных на главном сервере тоже высока, также включите Redis и задайте `SYNC_FREQUENCY` для периодической синхронизации конфигурации из базы данных.

Подробные способы использования переменных окружения см. [здесь](#-переменные-окружения).

### 🌐 Кластерное развертывание (децентрализованная схема)

Кластерный режим позволяет нескольким узлам развернуть собственные независимые One Api Pro + MySQL, с синхронизацией данных через события уровня приложения, без общей базы данных.

> **Подходящие сценарии**: глобальное развертывание в нескольких регионах, низкая задержка при обращении поблизости, высокая доступность и восстановление после сбоев, балансировка нагрузки между несколькими узлами.

#### 🗺️ Обзор архитектуры

```
                    ┌─────────────┐
                    │  Nginx/LB   │  （统一入口，ip_hash 负载均衡）
                    └──────┬──────┘
                           │
            ┌──────────────┼──────────────┐
            │              │              │
     ┌──────┴──────┐ ┌────┴───────┐ ┌───┴────────┐
     │  Node A     │ │  Node B     │ │  Node C     │
     │ (one-api-pro)   │ │ (one-api-pro)   │ │ (one-api-pro)   │
     │ + MySQL     │ │ + MySQL     │ │ + MySQL     │
     │ + Redis     │ │ + Redis     │ │ + Redis     │
     └──────┬──────┘ └─────┬──────┘ └────┬────────┘
            │              │              │
            └────── HTTP 推送同步事件 ──────┘
```

#### ⭐ Ключевые особенности

- **Децентрализация** — все узлы равноправны, без разделения на главный и подчинённый; после любого изменения данных узел активно рассылает его всем живым узлам
- **Нулевое вмешательство** — перехват изменений данных через колбэки GORM, без модификации существующего бизнес-кода
- **Асинхронная рассылка** — синхронизация данных не блокирует основной поток; выполняется пакетная рассылка в фоновой goroutine
- **Разрешение конфликтов** — сравнение по метке времени `updated_at`, записываются только более новые данные
- **Синхронизация лимитов** — счётчики конкурентности каналов и RPM синхронизируются между узлами через таблицы базы данных
- **Совместимость с одним узлом** — если не заданы переменные окружения кластера, система полностью работает в режиме одного узла

#### 📊 Область синхронизации

| Таблица данных | Синхронизируется | Описание |
|--------|---------|------|
| users | ✅ | информация о пользователях |
| tokens | ✅ | API-токены |
| channels | ✅ | конфигурация каналов |
| abilities | ✅ | возможности каналов |
| options | ✅ | настройки системы |
| redemptions | ✅ | коды пополнения |
| plans | ✅ | тарифные планы |
| user_plans | ✅ | подписки пользователей |
| plan_usages | ✅ | использование планов |
| channel_counters | ✅ | счётчики лимита частоты каналов |
| cluster_nodes | 🔄 Обнаружение | информация об узлах кластера (поддерживается механизмом обнаружения, не через синхронизацию данных) |
| logs | ⚠️ Опционально | большой объём данных журналов; управляется через `CLUSTER_SYNC_LOGS` |

#### 🚀 Шаги развертывания

**1. Конфигурация MySQL (каждый узел должен использовать независимый экземпляр MySQL)**

Каждому узлу нужен **независимый экземпляр MySQL** (нельзя создавать несколько баз данных в одном экземпляре MySQL для развертывания нескольких узлов, потому что `auto_increment_offset` — переменная уровня экземпляра).

```ini
# 节点 1 的 my.cnf
[mysqld]
server-id = 1
auto_increment_increment = 50
auto_increment_offset = 1
log_bin = mysql-bin
binlog_format = ROW

# 节点 2 的 my.cnf
[mysqld]
server-id = 2
auto_increment_increment = 50
auto_increment_offset = 2
log_bin = mysql-bin
binlog_format = ROW

# 节点 3 的 my.cnf
[mysqld]
server-id = 3
auto_increment_increment = 50
auto_increment_offset = 3
log_bin = mysql-bin
binlog_format = ROW
```

> `auto_increment_increment` задан равным 50 — поддерживается до 50 узлов. Значение `offset` каждого узла должно совпадать с `CLUSTER_NODE_ID` и не повторяться.

> **Важно:** `auto_increment_increment` и `auto_increment_offset` — это **системные переменные уровня MySQL**, они действуют на все базы данных в экземпляре. Невозможно задать разные значения для разных баз данных, а также на уровне таблицы (параметры таблиц MySQL поддерживают только начальное значение `AUTO_INCREMENT`, но не шаг). Поэтому каждый узел **обязан использовать независимый экземпляр MySQL** — нельзя развернуть несколько узлов в одном экземпляре MySQL, создавая разные базы данных. Если требуется запустить несколько экземпляров MySQL на одной машине, можно запустить несколько процессов mysqld на разных портах или использовать Docker для запуска нескольких независимых контейнеров MySQL.

> **По поводу `server-id` и binlog:** `server-id` должен различаться во всех экземплярах MySQL одного кластера. `log_bin` и `binlog_format=ROW` настоятельно рекомендуется включить — они нужны для будущего расширения репликации master-slave и восстановления на момент времени (point-in-time recovery). Сама синхронизация данных кластера не зависит от binlog (она реализована на уровне приложения через колбэки GORM), но binlog обеспечивает дополнительную надёжность.

**2. Конфигурация Redis (каждый узел должен использовать независимый экземпляр Redis)**

Каждому узлу также нужен **независимый экземпляр Redis** (на другом порту или на другой машине). В данной кластерной архитектуре Redis не используется для связи между узлами — только для кэша, лимитов частоты и других бизнес-задач данного узла.

**3. Инициализация данных нового узла**

При вводе нового узла в эксплуатацию сначала необходимо получить снимок данных существующего узла:

```bash
# 方式一：从已有节点导出并导入
mysqldump -h existing-node -u root -p oneapi > backup.sql
mysql -u root -p oneapi < backup.sql

# 方式二：通过 API 获取快照（需先启动服务）
curl -H "X-Cluster-Secret: your-secret" \
  "https://existing-node/api/cluster/snapshot?tables=users,tokens,channels,abilities,options,redemptions,plans,user_plans,plan_usages" \
  -o snapshot.json
```

**4. Конфигурация переменных окружения (полный пример)**

**5. Команды запуска**

Каждый узел загружает свой файл конфигурации через параметр `--env`:

```bash
# 节点 1
./one-api-pro --env /opt/one-api-pro/node1/.env --port 3000

# 节点 2
./one-api-pro --env /opt/one-api-pro/node2/.env --port 3001

# 节点 3
./one-api-pro --env /opt/one-api-pro/node3/.env --port 3002
```

**6. Порядок запуска**

1. Запустите первый узел (Node A), `CLUSTER_SEEDS` оставьте пустым или укажите его собственный адрес
2. Дождитесь полного запуска Node A (около 5–10 секунд, в журнале появится сообщение «модуль кластера инициализирован»)
3. Запустите последующие узлы, указав в `CLUSTER_SEEDS` адрес любого живого узла
4. После запуска последующие узлы автоматически пингуют узел-«семя» и транзитивно обнаруживают все остальные узлы
5. После запуска всех узлов состояние кластера можно просмотреть в админ-панели любого узла: **Настройки → Управление узлами**

**7. Пример конфигурации балансировки нагрузки Nginx (опционально)**

```nginx
upstream one_api_cluster {
    ip_hash;  # 基于 IP 哈希，同一用户请求固定到同一节点，保证 session/cache 命中
    server cn.example.com:3000;
    server us.example.com:3000;
    server eu.example.com:3000;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://one_api_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

> **Использование `ip_hash` имеет решающее значение** — оно гарантирует, что запросы одного и того же пользователя всегда попадают на один узел, избегая потери состояния ограничений частоты планов, кэша Redis и т.п. между узлами.

**8. Проверка состояния кластера**

После завершения развертывания проверить можно следующим образом:


Или в админ-панели: **Настройки → Управление узлами** — просмотр списка узлов, состояния, времени последнего heartbeat и т.д.

#### ⚠️ Важные замечания

- У каждого узла должен быть независимый экземпляр MySQL и Redis; общая база данных не допускается
- `CLUSTER_SECRET` должен быть одинаковым на всех узлах; используйте надёжный пароль и храните его в безопасности
- `CLUSTER_NODE_ID` должен различаться на всех узлах и совпадать с `auto_increment_offset` MySQL
- `CLUSTER_NODE_ADDRESS` должен быть публичным адресом, доступным другим узлам (нужен префикс протокола, например `https://`)
- Инициализация данных перед вводом нового узла в эксплуатацию выполняется вручную (снять снимок с онлайн-узла)
- Таблица журналов (logs) содержит большой объём данных; синхронизацию журналов можно отключить через `CLUSTER_SYNC_LOGS=false`
- `auto_increment_increment` и `auto_increment_offset` MySQL должны соответствовать конфигурации `CLUSTER_NODE_ID`
- Обнаружение узлов использует двунаправленный ping; отказавшие узлы не удаляются, а только помечаются как status=2; после восстановления сети автоматически «оживают»
- `CLUSTER_SEEDS` — только начальная загрузка; как только узлы обнаруживают друг друга через ping, опора на SEEDS больше не требуется
- Изменения, произведённые на других узлах, пока узел был офлайн, **не пересылаются автоматически**; после возврата онлайн такому узлу нужно снять снимок для восполнения данных

#### 📝 О саморегистрации «локального узла»

Каждый узел при запуске записывает в собственную таблицу `cluster_nodes` локальную запись (значение `node_id` равняется заданному у себя `CLUSTER_NODE_ID`). Это **намеренная разработка**, по следующим причинам:

1. **Отображение в админ-панели** — на странице «Настройки → Управление узлами» администратору необходимо видеть информацию о своём узле (адрес, состояние, время heartbeat и т.д.), чтобы диагностировать неполадки
2. **Транзитивность обнаружения узлов** — когда узел B получает ping от узла A, A возвращает в ответе полный список узлов (включая сам A). B объединяет его со своей локальной таблицей. Так C через ответ B также узнаёт о существовании A
3. **Основа для определения живости** — значение `last_heartbeat` локальной записи автоматически обновляется этим узлом каждые 30 секунд (в функции `discoverOnce`), отражая нормальное состояние работы узла

**Саморегистрация не приводит к циклической синхронизации данных.** Система защищена на 5 уровнях:

| Точка защиты | Назначение |
|---|---|
| ① `GetAllRemoteNodes` SQL-фильтр | при обнаружении в SQL добавляется `node_id != ?` для исключения собственного узла |
| ② `GetAliveNodesForSync` SQL-фильтр | при рассылке в SQL добавляется `node_id != ?` для исключения собственного узла |
| ③ `handlePing` отклоняет собственный ping | явное отклонение `req.NodeId == NodeID` |
| ④ `mergeDiscoveredNodes` пропускает собственный узел | при объединении обнаруженных узлов собственный узел пропускается |
| ⑤ `ApplyEvents` пропускает собственные события | при применении событий игнорируются события, порождённые собственным узлом |

Поток данных однонаправленный: с локального узла на удалённые, с удалённых на локальный узел — **замкнутых циклов никогда не возникает**.

Админ-панель отображает рядом с именем локального узла синий значок «локальный», а для собственного узла отключает операции «Удалить» и «Ручной ping» (для собственного узла они бессмысленны).

#### 🔐 О «независимом секрете на каждом узле»

У каждого узла есть **собственный секрет**, общий глобальный секрет больше не используется. Причины такой разработки:

1. **Безопасность** — утечка секрета одного узла не затрагивает другие узлы
2. **Гибкость управления** — каждый узел может независимо ротировать собственный секрет
3. **Автоматическое обнаружение** — при ping между узлами секрет передаётся автоматически для сохранения у противоположной стороны

**Жизненный цикл секрета:**
- Первый запуск узла: переменная окружения `CLUSTER_SECRET` используется как начальное значение и записывается в поле `cluster_nodes.secret_key`
- Последующие запуски: значение читается из `cluster_nodes.secret_key`
- Admin может изменить секрет других узлов на странице «Управление узлами»
- Значение заголовка `X-Cluster-Secret` при ping = **секрет целевого узла** (берётся из локальной БД)

**Процесс добавления нового узла:**
1. На узле A добавьте запись узла B, указав значение `CLUSTER_SECRET` узла B
2. На узле B добавьте запись узла A, указав значение `CLUSTER_SECRET` узла A
3. A пингует B: используется секрет B; B принимает: проверяет собственный секрет ✓
4. В ответе B передаются секреты A и B, A обновляет их локально

#### 🗑️ О «мягком удалении узла»

При удалении узла admin **не удаляет запись физически**, а устанавливает `disabled = true`:

- Защищает от «автоматического возврата» удалённого узла (механизм ping перерегистрирует его)
- Отключённый узел всё ещё отвечает на ping (чтобы другие знали, что он онлайн), но не получает информацию об этом узле
- Физическое удаление требует ручного SQL: `DELETE FROM cluster_nodes WHERE node_id = ?`

#### 🔄 О «механизме синхронизации данных» (важно)

**Синхронизация данных кластера** полностью опирается на механизм **событий GORM + активной HTTP-рассылки**:
- Любая операция INSERT/UPDATE/DELETE в бизнес-таблице → перехватывается колбэком GORM → записывается в таблицу `sync_events` → Pusher-goroutine рассылает всем живым узлам
- Получатель записывает в локальную базу данных через `WithSkipHook` (без зацикливания)
- Получатель пропускает события с `event.NodeId == локальный NodeID` (двойная защита)

**Компромисс архитектуры:** данная разработка **не реализует активную выборку между узлами**, по следующим причинам:
1. **Вторжение в бизнес** — межузловая выборка требует знания бизнес-уникальных полей каждой таблицы, что вторгается в бизнес-код
2. **Конфликт первичных ключей** — автоинкрементные ID между узлами не являются непрерывными (разные `auto_increment_offset`); использование исходного id нарушит схему offset
3. **Высокая сложность** — высокие затраты на обслуживание, ограниченный прирост надёжности
4. **Активной рассылки достаточно** — 95% сценариев (обычная синхронизация при онлайн-узлах) полностью покрываются рассылкой

**Известные ограничения и требования по эксплуатации:**
- Изменения данных, произошедшие на других узлах во время офлайна узла → **теряются безвозвратно** (рассылка выполняется в реальном времени)
- После возврата узла в сеть данные за время офлайна не восполняются автоматически
- Новый узел получает только те изменения, которые произошли после его ввода в кластер, исторических данных нет
- **Мера восстановления для эксплуатации:** экспортируйте данные с другого узла через `mysqldump` и импортируйте

**Сопоставление типовых сценариев развертывания:**

| Сценарий | Нужна ли выборка | Как решается |
|---|---|---|
| Узел постоянно в сети | ❌ | рассылка полностью покрывает |
| Узел эпизодически перезапускается (минуты) | ⚠️ | кратковременная потеря данных за офлайн, для эксплуатации приемлемо |
| Узел часто обслуживается | ❌ | рассылка продолжается, после перезапуска сразу восстанавливается |
| Новый узел входит в кластер | ❌ | DBA вручную через `mysqldump` выполняет инициализацию |
| Узел восстанавливается после длительного офлайна | ❌ | DBA вручную через `mysqldump` восполняет данные |

Если после развертывания при обращении появляется пустая страница, см. [#97](https://github.com/modelbus/one-api-pro/issues/97).
